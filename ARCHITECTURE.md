# ARCHITECTURE.md — Homelab Bot

## Суть проекта

Telegram-бот на Rust, живущий в приватном чате с единственным разрешённым пользователем. Использует Forum Topics (Threaded Mode) вместо отдельного webapp — вся функциональность идёт через топики внутри одного чата с ботом.

## Конфигурация

### .env (секреты, не коммитится)

- `BOT_TOKEN` — токен бота
- `CHAT_ID` — ID приватного чата
- `NOTIFY_SERVER_PORT` — порт HTTP-сервера для приёма внешних нотификаций
- `NOTIFY_TOKEN` — токен авторизации для HTTP-эндпоинта `/notify`
- `NOTES_ROOT` — абсолютный путь для хранения быстрых заметок (`.md` файлы)
- `DEBOUNCE_SECS` — таймер дебаунса в секундах (по умолчанию 45)

### config.json (коммитится)

- `notifications` — thread_id топика "Уведомления"
- `quick_notes` — thread_id топика "Быстрые заметки"

Заполняется автоматически при первом запуске. Если файл отсутствует или пуст — бот создаёт топики через Bot API и записывает полученные `thread_id` в `config.json`.

## Архитектура запуска

Бот запускает 5+ независимых tokio-задач в одном процессе:

```
main.rs
├── task: Router (teloxide Dispatcher, НЕ supervised)
│   ├── to_thread_handler → Быстрые заметки (фильтр по thread_id)
│   └── callback_handler → обработка inline-кнопок
│
├── task: HTTP-сервер (axum, supervised)
│   └── ловит нотификации с локалки → очередь → worker → "Уведомления"
│
├── task: Notification worker (НЕ supervised)
│   └── забирает задачи из SQLite-очереди, шлёт в телеграм
│
├── task: Heartbeat updater ×2 (НЕ supervised)
│   └── обновляет описание чата статусом модулей
│
└── task: Stats cleanup (НЕ supervised)
    └── периодически чистит старую статистику из SQLite
```

Только HTTP-сервер обёрнут в `run_supervised` (`src/supervisor.rs`). Остальные — обычные `tokio::spawn`. Падение роутера роняет весь процесс (защита через `systemd Restart=on-failure`).

Общее состояние через `Arc`:
- `Arc<Bot>` — отправка сообщений
- `Arc<Config>` — thread_id, токены, порты
- `Arc<SqlitePool>` — очередь уведомлений, статистика
- `Arc<BotStart>` — uptime для `/status`
- `Arc<Heartbeat>` — статус модулей для описания чата
- `Arc<Mutex<Instant>>` — alive-таймеры модулей

## Модули

### 1. Быстрые заметки

Топик "Быстрые заметки". Пользователь пишет текстовые сообщения прямо в этот топик, бот слушает входящие сообщения, отфильтрованные по `message_thread_id`, и сохраняет в `NOTES_ROOT` как `.md` файлы.

#### Константы

```rust
const TITLE_MAX_LEN: usize = 50;
```

#### Состояние

Один активный буфер на топик. Хранится в `Arc<Mutex<Option<InboxBuffer>>>`:

```rust
struct InboxBuffer {
    file_path: PathBuf,
    close_handle: JoinHandle<()>,
    feedback_msg_id: MessageId,
}
```

#### Логика на каждое входящее сообщение

Сначала определяется, является ли сообщение **явным заголовком** (title marker): первая строка текста начинается с `!`. Если да — всё, что идёт после `!` на этой же строке (до конца строки), становится заголовком; остаток сообщения (если после первой строки есть текст) идёт в тело файла как обычно. Символ `!` в сам файл не попадает.

**Ветки:**

1. **Нет `!`-маркера И буфер пуст (окно неактивно):**
   - Имя файла = `{timestamp}.md` (только дата/время).
   - Контент записывается целиком (включая первую строку).

2. **Нет `!`-маркера И буфер уже активен (окно продлевается):**
   - Дописать в конец текущего файла целиком, продлить таймер.

3. **Есть `!`-маркер И буфер пуст (окно неактивно):**
   - Заголовок = текст после `!` на первой строке.
   - Имя файла = `{timestamp}_{slug}.md`.
   - Первая строка (с `!`) пропускается при записи в файл.
   - Остаток сообщения (строки после первой, если есть) — в тело файла.

4. **Есть `!`-маркер И буфер уже активен (окно продлевается):**
   - **Принудительное закрытие текущего окна** (сброс `close_handle`, обнуление `Option<InboxBuffer>`) без ожидания истечения таймера.
   - Заголовок = текст после `!`.
   - Создание **нового** файла.
   - Первая строка пропускается, остаток — в тело нового файла.
   - Запуск нового окна на `DEBOUNCE_SECS`.

Смысл: `!`-маркер — это ручной override дебаунс-таймера и способ задать осмысленное имя файлу. Без маркера бот просто группирует сообщения по времени, не пытаясь угадать тему. С маркером — создаёт файл с читаемым именем и принудительно начинает новую группу.

Если сообщение состоит только из `!` без текста после — это невалидный маркер (пустой заголовок). Поведение — как будто маркера не было (дата/время в имени, контент целиком); не паниковать, не игнорировать сообщение молча.

При создании нового файла, если имя уже существует — добавляется суффикс `-2`, `-3` и т.д. (например `2026-07-04_21-03-2.md`).

#### Запись на диск

Запись происходит **сразу**, на каждое сообщение, а не по таймеру. Таймер отвечает только за то, продолжает ли следующее сообщение писаться в этот же файл или откроет новый. Это даёт устойчивость к падению процесса — максимум что теряется при рестарте это "какой файл сейчас активен", не сами данные.

При наличии `!`-маркера первая строка пропускается при записи в файл (она уже в имени файла). Без маркера записывается весь текст целиком.

#### slugify()

- Кириллица остаётся как есть
- Пробелы → `-`
- Вырезаются: `/ \ : * ? " < > | #` и управляющие символы
- Множественные `-` схлопываются, ведущие/хвостовые обрезаются

```rust
fn slugify(s: &str) -> String {
    let cleaned: String = s
        .chars()
        .filter(|c| !"/\\:*?\"<>|#".contains(*c))
        .collect();
    let slug = cleaned
        .split_whitespace()
        .collect::<Vec<_>>()
        .join("-");
    slug.trim_matches('-').to_string()
}
```

#### extract_explicit_title()

```rust
fn extract_explicit_title(text: &str) -> Option<&str> {
    let first = text.lines().next().unwrap_or(text);
    let rest = first.strip_prefix('!')?;
    let trimmed = rest.trim();
    if trimmed.is_empty() { None } else { Some(trimmed) }
}
```

`extract_explicit_title` возвращает `Some(заголовок)` если первая строка начинается с `!` и после него остаётся непустой текст. `None` — если маркера нет, либо после `!` только пробелы.

#### truncate_at_word_boundary()

```rust
fn truncate_at_word_boundary(s: &str, max_len: usize) -> &str {
    if s.chars().count() <= max_len {
        return s;
    }
    let end = s.char_indices()
        .nth(max_len)
        .map(|(i, _)| i)
        .unwrap_or(s.len());
    let truncated = &s[..end];
    truncated.rfind(' ').map_or(truncated, |i| &truncated[..i])
}
```

Версия с исправленным off-by-one (старая через `take(max_len).last()` теряла на один символ больше лимита) и с обязательно сохранённой ранней проверкой `chars().count() <= max_len`. Без этой проверки функция режет по последнему пробелу даже строки, которые изначально короче лимита.

#### Формат файла

Без `!`-маркера:
```markdown
---
created: {ISO8601 timestamp}
source: telegram
---

{полный текст сообщения}
```

С `!`-маркером:
```markdown
---
created: {ISO8601 timestamp}
source: telegram
---

{текст сообщения без первой строки (с !)}
```

**Пример без `!`-маркера** — три сообщения подряд, одно окно:

Сообщения:
```
Надо пересмотреть debounce окно для inbox бота
Может 45 сек мало, буду печатать по частям и рвать мысль
Или наоборот слишком много и будет объединять разные темы
```

Имя файла: `2026-07-04_21-03.md`

```markdown
---
created: 2026-07-04T21:03:11+03:00
source: telegram
---

Надо пересмотреть debounce окно для inbox бота

Может 45 сек мало, буду печатать по частям и рвать мысль

Или наоборот слишком много и будет объединять разные темы
```

**Пример с `!`-маркером** — пользователь начинает новую тему:

Сообщение:
```
! Сайт-визитка
Нужен лендинг для проекта
```

Имя файла: `2026-07-04_21-15_Сайт-визитка.md`

```markdown
---
created: 2026-07-04T21:15:42+03:00
source: telegram
---

Нужен лендинг для проекта
```

#### Фильтрация

Обработчик подписывается только на `msg.text()` (text + caption). Нетекстовые сообщения (фото/голос/файлы) молча игнорируются.

#### Подмодули

`src/modules/quick_notes/`:
- `handler.rs` — логика окон, запись на диск, helper-функции (`extract_explicit_title`, `slugify`, `truncate_at_word_boundary`)
- `format.rs` — манипуляции с содержимым файла: `replace_message()`, `append_message()`, `find_message()` (поиск сообщения по `---N---` разделителю)
- `rich_client.rs` — `RichClient`: обёртка над frankenstein для rich-сообщений с inline-кнопками (обратный отсчёт окна)

#### Редактирование сообщений

При редактировании (`msg.edit_date().is_some()`) бот заменяет содержимое соответствующего сообщения в файле через `format::replace_message()`. Сообщения идентифицируются по порядковому номеру в `---N---` разделителе.

#### Callback-кнопки

Окно с обратным отсчётом содержит inline-кнопку «закрыть окно». Нажатие отправляет `CallbackQuery` → `callback_handler` в роутере вызывает `handler.rs`, который:
1. Закрывает текущий буфер
2. Удаляет сообщение с кнопкой
3. Отправляет подтверждение «📁 Окно закрыто»

#### Проверка NOTES_ROOT

Бот НЕ создаёт `NOTES_ROOT` директорию. Наличие `NOTES_ROOT` — инфраструктурная ответственность окружения. Молчаливое создание скрывает реальную проблему конфигурации. При старте — явная проверка, fail fast:

```rust
if !root.is_dir() {
    panic!("NOTES_ROOT path {:?} does not exist or is not a directory. \
            Create it manually before starting the bot.", root);
}
```

С `systemd Restart=on-failure` это даёт понятный сигнал (процесс не поднимается, причина видна в логах) вместо тихого расхождения данных.

### 2. Уведомления

Топик "Уведомления". Только вывод от бота в чат, пользователь туда не пишет.

Источник — независимый существующий Python-скрипт бэкапа (не трогаем). Канал доставки — внутренний HTTP на порту `NOTIFY_SERVER_PORT`.

#### Эндпоинт

```
POST /notify
Content-Type: multipart/form-data
Authorization: Bearer {NOTIFY_TOKEN}
```

Поля формы:

| Поле | Тип | Обязательно | Описание |
|------|-----|-------------|----------|
| `message` | строка | да | Текст уведомления |
| `level` | строка | нет | `info` / `warning` / `error`, дефолт `info`. Приводится к эмодзи: 🔵 / 🟡 / 🔴 |
| `source` | строка | нет | Происхождение алерта |
| `file` | файл | нет | **Разбирается, но отбрасывается** — отправка файлов в телеграм не реализована |

Эндпоинт принимает только `multipart/form-data`. `application/json` не поддерживается.

Невалидный формат, отсутствие `message` или пустая строка после `trim()` → `400 Bad Request`.

#### Доставка в телеграм

Нотификация не отправляется сразу — она попадает в **SQLite-очередь** (`TaskQueue` в `src/queue.rs`). Фоновый воркер (`src/worker.rs`) забирает задачи, отправляет `bot.send_message` с дедупликацией (5-минутное окно, `src/dedup.rs`) и повторяет до 5 попыток при ошибке.

Формат сообщения:
```
[{эмодзи}] {source}: {message}
```

Если `source` отсутствует:
```
[{эмодзи}]: {message}
```

#### Ответ клиенту

- `200 OK` — запрос принят в очередь, **не дожидаясь отправки в телеграм**
- `400 Bad Request` — невалидное тело запроса
- `401 Unauthorized` — неверный/отсутствующий токен

#### Авторизация

Статический токен в `.env`:

```
NOTIFY_TOKEN=<случайная строка>
```

Проверка — middleware, сверяющий заголовок `Authorization: Bearer {token}` с `NOTIFY_TOKEN` из конфига. Несовпадение или отсутствие заголовка → `401 Unauthorized`. Обычное `==` по строке допустимо (локальная сеть, токен не передаётся по внешним каналам).

## Маршрутизация (`src/router.rs`)

`Router` — центральный диспетчер сообщений для teloxide. Настраивает три параллельных handler'а:

- **`to_thread_handler`** — направляет сообщения в топик "Быстрые заметки" (фильтр по `message_thread_id`)
- **`callback_handler`** — обрабатывает нажатия inline-кнопок (например, «закрыть окно»)
- **`status_handler`** — команда `/status` — показывает uptime и статистику за сегодня

Редактированные сообщения обрабатываются отдельным `Update::filter_edited_message()` — при редактировании заменяется содержимое соответствующего сообщения в файле заметки.

## Очередь уведомлений (`src/queue.rs`, `src/worker.rs`)

`TaskQueue` — generic SQLite-backed очередь задач с операциями:

- `insert` — добавить задачу в очередь
- `claim` — взять следующую задачу в статусе `pending` (с блокировкой через `processing`)
- `mark_done` — пометить как выполненную
- `mark_pending_retry` — вернуть в очередь для повторной попытки
- `mark_failed` — пометить как проваленную (после исчерпания всех попыток)

`spawn_notification_worker()` — фоновый воркер, который в цикле:
1. Забирает задачу из очереди
2. Проверяет дедупликацию (`DedupCache`, 5-минутное окно)
3. Отправляет `bot.send_message` в топик уведомлений
4. При ошибке — возвращает задачу в очередь (до `max_attempts = 5`)

Retry-задержка не экспоненциальная — воркер просто перезабирает задачу при следующей итерации.

## Дедупликация (`src/dedup.rs`)

`DedupCache` — in-memory кеш с 5-минутным TTL, ключ — `(chat_id, thread_id, message_text)`. Повторные нотификации с тем же текстом в пределах окна отбрасываются, чтобы не спамить в чат при частых срабатываниях скрипта.

## Статистика (`src/stats.rs`)

- `BotStart` — хранит `Instant` старта бота для подсчёта uptime
- `StatsSnapshot` — дневная статистика (сообщения/редактирования/нотификации)
- `record_stat()` — инкрементит счётчик в SQLite
- `query_today()` — достаёт статистику за сегодня
- `cleanup_expired()` — удаляет записи старше 7 дней

Команда `/status` возвращает:
```
Homelab Bot v0.4.0
Uptime: 2d 3h 15m
Сегодня: 5 сообщений, 2 редактирования, 3 уведомления
```

## Heartbeat (`src/heartbeat.rs`)

`Heartbeat` — реестр модулей с `ModuleHandle`. Каждый модуль регистрирует своё имя, `Instant` последней активности и check-функцию.

При старте и раз в час (`/status` + часовой таймер) бот обновляет `set_chat_description` в телеграме, выводя список модулей:
```
🟢 quick_notes: 2m ago
🟢 http_notifications_server: 5s ago
```

Модуль, который не обновлял `alive` дольше порога (обычно 2× интервал), показывается жёлтым (⚠️) или красным (🔴).

## База данных (`src/db.rs`)

SQLite через `sqlx` с пулом соединений. Две таблицы:

- `pending_notifications` — очередь уведомлений (id, chat_id, thread_id, kind, text, status, attempts, max_attempts, timestamps)
- `stats` — дневная статистика (date, module, msg_count, edit_count, notif_count, timestamps)

Инициализация — `init_db()`, вызывается при старте, создаёт таблицы через `CREATE TABLE IF NOT EXISTS`.

## Самообновление

Флаг `--update` запускает `self_update()` (`src/main.rs`):
1. Показывает текущую версию (`CARGO_PKG_VERSION`)
2. GET на GitHub Releases API — показывает последний тег
3. Если версии совпадают → `Already up to date!`
4. Если есть новая — скачивает `homelab-bot` из ассетов релиза в `homelab-bot.new`
5. `self_replace::self_replace("homelab-bot.new")` — атомарная замена бинарника
6. `std::process::exit(0)` — process exits, systemd перезапускает с новым бинарём
